# 새 게임 개발 사전 구성 지침서

이 문서 하나를 새 프로젝트의 Codex에 전달하면 게임 개발 전에 필요한 문서, 프로젝트 전용 스킬, 작업 절차와 구조 검사를 구성할 수 있다. 다른 저장소의 파일이나 설치된 플러그인은 필요하지 않다. 마지막의 Forest Arena 자료는 작성 근거이며 구성에 필요한 입력이 아니다.

초기 구성의 완료점은 **개발을 시작할 준비**다. 게임 코드·장면·실행 프로젝트·서버·DB·최종 자산은 만들지 않는다. 엔진 공통 구성을 먼저 만들고, 사용자가 선택한 경우에만 Godot·Android 준비 문서를 추가한다. 엔진과 도구가 미정이어도 공통 구성을 완료할 수 있다.

## 1. Codex에 전달할 시작 요청문

아래 요청문과 입력 양식을 함께 전달한다. 빈칸은 모른다는 뜻이며 동의나 승인이 아니다.

```text
첨부한 새 게임 개발 사전 구성 지침서를 따라 현재 폴더를 준비해 주세요.
먼저 기존 파일과 사용자 지시를 확인하고 필요한 부분만 보완해 주세요.
중요한 입력이 빠졌으면 기존 문서에서 먼저 찾고, 남은 질문은 한 번에 묶어 주세요.
미정 사항은 proposed(제안)로 기록하고 확정된 것처럼 구현하지 마세요.
문서·필요한 프로젝트 전용 스킬·작업 절차·구조 검사까지 진행해 주세요.
게임 코드 작성, 도구 설치, 계정 연결, Git 원격 변경은 이번 요청에 포함하지 않습니다.
기본은 단일 에이전트로 진행하고 기존 결정·파일·사용자 변경을 보존해 주세요.
끝나면 변경 파일, 검사 결과, 실패·미실행 항목, 미정 결정과 다음 작업을 보고해 주세요.
```

### 입력 양식

| 항목 | 작성할 값 | 미정일 때 처리 |
| --- | --- | --- |
| 게임 이름 | 표시할 이름 | 임시 표시 이름을 제안하고 확인 |
| 프로젝트 ID | 소문자 영문·숫자·하이픈, 예: `cloud-garden` | 폴더·스킬 이름에 쓸 임시 ID를 제안하고 확인 |
| 핵심 플레이 | 플레이어가 반복하는 행동과 얻는 재미를 1~3문장으로 설명 | 범위를 정하는 핵심 질문으로 묶어서 확인 |
| 대상 플랫폼 | PC·Android·iOS·웹 등, 우선순위 | 우선 대상 또는 미정 유지 여부 확인 |
| 엔진 | 엔진 이름·알고 있는 버전 또는 `미정` | 공통 구성만 진행, 설치·엔진 전용 명령 보류 |
| 화면·입력 | 가로/세로/가변, 터치·키보드·패드 등 | 대상 플랫폼과 함께 확인하거나 제안으로 보존 |
| 첫 개발 목표 | 처음 만들고 확인할 플레이 흐름 | 핵심 플레이와 함께 확인 |
| 제외 기능 | 이번에 만들지 않을 것 | 사용자에게 확인할 목록으로 제안 |
| 선택 도구 | 디자인·이미지·오디오·이슈 관리 도구, 플러그인 또는 `없음` | 없음으로 진행 가능, 필요하면 후보만 제안 |
| Git 운영 | 기존 저장소 여부, 원하는 브랜치·PR 절차 | 로컬 파일 작업만 진행, 원격 정책 제안 보류 |
| 환경 제약 | 운영체제, 사용 가능한 Python 3, 기기, 예산·일정 등 | 발견한 환경과 미확인 환경을 구분 |

기존 문서에서 확인한 값에는 출처 경로를 적는다. 게임 이름·ID·핵심 플레이·첫 목표가 없거나 서로 충돌하면 관련 질문을 한 번에 묶는다. 플랫폼과 입력은 첫 목표를 바꿀 만큼 중요한 경우 함께 묻는다. 사용자가 `미정으로 진행`을 선택하면 임시 이름·ID를 확인한 뒤 나머지는 제안으로 남긴다. 질문에 답이 없는 동안은 파일 조사와 요청 기록만 진행하고, 중요한 값을 임의 확정하지 않는다.

결정 상태는 `proposed`(제안), `accepted`(사용자가 승인함), `superseded`(다른 결정으로 대체됨)로 쓴다. 답변·기존 승인 근거 없이 `accepted`로 올리지 않는다. 미정 엔진·성능 목표·출시 패키지 ID는 초기 구성 완료를 막지 않는다.

### 이름과 명령 치환 규칙

- 이 문서에서 `{{GAME_NAME}}`은 표시 이름, `{{PROJECT_ID}}`는 프로젝트 ID, `{{TOPIC}}`은 작업 이름이다. 실제 생성 파일에서는 치환 표시를 남기지 않는다.
- 프로젝트 ID는 `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`로 제한한다. Python 모듈 이름이 필요하면 하이픈을 밑줄로 바꾼 별도 값을 기록한다. 출시 패키지 ID는 이 값에서 자동 확정하지 않는다.
- 스킬은 `{{PROJECT_ID}}-workflow`처럼 이름 짓고 폴더 이름과 YAML의 `name`을 일치시킨다. 명령과 경로에는 실제 생성한 이름만 쓴다.
- `Forest Arena`, `ForestArena`, `forest-arena`, `forest_arena`, `ForestTales`, `com.forestarena`, `com.foresttales`, `ForestArenaResources`를 새 설정·명령·스킬에 복사하지 않는다. 이 지침서의 참고 설명은 예외다.
- 기존 프로젝트의 이름·명령·ID는 사용자의 변경 요청 없이는 치환하지 않는다. 기존 값이 예시 금지어와 같다면 검사에서 해당 경로·이유를 좁게 예외로 기록한다. 전체 검사 제외는 하지 않는다.

## 2. 생성할 파일과 작성 규칙

다음은 새 프로젝트의 기본 구조다. 기존 프로젝트에 같은 역할을 하는 파일이 있으면 경로를 유지하고 색인·검사가 그 경로를 사용하도록 맞춘다. 빈 템플릿을 추가해 같은 기준을 둘로 만들지 않는다.

```text
AGENTS.md
README.md
docs/INDEX.md
docs/product/vision.md
docs/product/roadmap.md
docs/product/decisions.md
docs/engineering/architecture.md
docs/content/art-and-audio.md
docs/operations/ai-development.md
docs/operations/harness/team-spec.md
docs/operations/harness/operating-index.md
.agents/skills/{{PROJECT_ID}}-workflow/SKILL.md
scripts/verify-docs.sh
scripts/verify-harness.sh
scripts/verify.sh
tools/verify_bootstrap.py
_workspace/bootstrap/00_request.md
_workspace/bootstrap/04_closeout.md
```

`docs/GLOSSARY.md`는 여러 문서에서 반복되는 낯선 전문 용어가 생길 때 추가한다. 전문 용어의 첫 등장에는 쉬운 뜻을 붙인다. 짧은 단일 작업을 위해 역할별 문서나 스킬을 모두 만들지 않는다. 기본 스킬 하나로 충분하면 그것만 만든다.

| 파일 | 반드시 작성할 내용 |
| --- | --- |
| `AGENTS.md` | 목적, 색인 경로, 기록·검사 명령, 기존 결정 보존, 단일 에이전트 원칙. 상세 규칙은 링크 |
| `README.md` | 한 줄 소개, 플랫폼·엔진 상태, 준비된 것·미구현, 시작 순서, 실제 가능한 검사 명령, 문서 충돌 처리 |
| `docs/INDEX.md` | 처음 읽는 순서, 질문별 문서 경로, 폴더 역할. 새 문서는 여기 연결 |
| `vision.md` | 핵심 재미, 대상 사용자·플랫폼·입력, 첫 목표, 포함·제외 범위, 미정 사항 |
| `roadmap.md` | 사전 구성 → 첫 플레이 흐름 → 다음 검증 순서, 각 완료 조건·의존 조건·제외 범위. 게임 단계 번호는 새로 정함 |
| `decisions.md` | 결정 ID·제목·상태·날짜·근거·내용·영향·대체 관계. 미정은 제안으로 기록 |
| `architecture.md` | 엔진 선택 상태, 구현·표현·데이터의 책임 구분, 저장·공용 ID 변경 절차, 향후 실행·검사 환경. 미구현 구조는 계획으로 표시 |
| `art-and-audio.md` | 시각·소리 방향의 제안, 제작·승인·등록·실제 연결 구분, 출처·이용 조건 기록, 임시 자산 방침 |
| `ai-development.md` | 조사 → 요청 → 필요한 설계 → 작성 → 검사 → 마무리, 조건부 기록과 실패 처리 |
| `team-spec.md` | 활성 역할과 책임·스킬 대응의 단일 목록, 역할 합치는 기준, 요청별 담당 선택, 전달·검토·실패 처리 |
| `operating-index.md` | 현재 단계, 실제 검사 명령·필요 환경, 미확인 사항과 재개 조건. 역할 목록은 팀 명세로 연결 |
| `SKILL.md` | YAML 이름·설명, 사용 시점, 필수 입력, 작업 흐름, 산출물과 검증 |
| 검사 파일 | 아래 7절의 구조 검사. 엔진·게임 실행이나 원격 연결을 요구하지 않음 |
| 작업 기록 | 요청·범위·완료 조건과 실제 변경·검사·남은 일. 성공하지 않은 결과를 통과로 기록하지 않음 |

### 짧은 AGENTS.md 핵심 템플릿

아래 내용의 값을 채우고 프로젝트 전체에 반복 적용할 규칙만 남긴다. 기존 파일은 필요한 문장만 보완한다.

```markdown
# {{GAME_NAME}} 작업 안내

- 목적과 현재 범위는 README.md, 문서 위치는 docs/INDEX.md에서 확인한다.
- 쉬운 한국어를 먼저 쓰고 전문 용어는 처음에 뜻을 설명한다.
- 역할과 담당 선택은 docs/operations/harness/team-spec.md 한 곳에서 관리한다.
- 기본은 단일 에이전트다. 역할 구분만으로 다른 에이전트를 실행하지 않는다.
- 기존 결정과 사용자 변경을 보존한다. 미정은 proposed로 기록한다.
- 작업마다 _workspace/<topic>/00_request.md와 04_closeout.md를 남긴다.
- 문서 검사: ./scripts/verify-docs.sh
- 스킬·역할 검사: ./scripts/verify-harness.sh
- 전체 구조 검사: ./scripts/verify.sh
- 게임 구현 전까지 실행·기기 검사는 미실행으로 표시한다.
```

### README·색인·제품 문서 핵심 템플릿

다음 필드를 각 파일에 작성한다. 양식만 남기지 말고 입력 양식에서 얻은 내용과 `미정`을 넣는다.

```text
README.md
  소개: 게임 이름, 핵심 플레이 한 문장
  환경: 대상 플랫폼, 엔진과 버전의 확정 여부
  현재: 사전 구성 완료 여부 / 게임 코드 미구현
  읽는 순서: docs/INDEX.md → 제품 방향 → 개발 순서 → 운영 색인
  검사: 세 검사 명령과 Python 3 필요 여부
  충돌: 사용자의 현재 지시와 명시적 승인 근거부터 확인한다.
        README·분야 문서와 승인 결정이 충돌하면 한쪽을 조용히 덮어쓰지 않고
        출처를 기록해 질문한다. 작업 기록은 승인 결정을 대신하지 않는다.

docs/INDEX.md
  처음 읽기: README, vision, roadmap, operating-index
  목적별 표: 제품 / 결정 / 기술 / 콘텐츠 / 작업 절차 / 역할 / 현재 검사
  폴더 설명: product, engineering, content, operations, .agents/skills, _workspace
  문서별 최종 기준 위치: 각 규칙의 원본 한 곳을 지정하고 나머지는 링크

docs/product/vision.md
  게임 이름·핵심 재미 / 사용자·플랫폼·화면·입력
  첫 개발 목표 / 이번 포함 범위 / 제외 기능 / 미정과 결정 ID

docs/product/roadmap.md
  사전 구성: 문서·스킬·구조 검사 통과
  첫 플레이 흐름: 핵심 입력 → 상태 변화 → 결과 확인의 구체적 완료 조건
  다음 개발: 첫 흐름 확인 뒤에 할 일과 아직 하지 않을 일
  각 단계: 시작 조건 / 산출물 / 검사 / 상태
```

결정 한 건의 템플릿은 아래와 같다. 사용자 답변 자체로 확정된 입력에는 날짜와 해당 답변 요약을 근거로 적는다.

```markdown
## DEC-001: 엔진 선택

- 상태: proposed
- 날짜: 작성일
- 근거: 사용자 입력의 엔진 미정
- 제안: 후보와 선택 이유, 아직 필요한 확인
- 영향: 엔진 전용 설정과 실행 검사는 보류, 공통 구성은 진행
- 대체 관계: 없음
```

## 3. 역할 선택과 스킬 작성

역할은 책임의 구분이다. 에이전트 수와 다르며 한 에이전트가 여러 역할을 순서대로 수행할 수 있다. 아래 일곱 책임이 빠지지 않게 팀 명세에 배정하되 작은 프로젝트는 세 역할 정도로 합친다.

| 책임 | 담당할 일 | 작은 프로젝트에서 합치는 예 |
| --- | --- | --- |
| 제품 | 재미·범위·개발 순서·완료 조건·미정 결정 | 기획·콘텐츠 |
| 게임 구현 | 규칙·입력·상태·결과, 실행 가능한 코드 | 개발 |
| UI | 화면 흐름·가독성·입력 안내 | 개발 |
| 콘텐츠 | 이미지·모션·소리·출처·승인 상태 | 기획·콘텐츠 |
| 플랫폼 | 빌드·입력 장치·중단/복귀·성능 확인 | 개발 |
| 공용 데이터 | 여러 코드가 함께 쓰는 형식·ID·저장 버전 | 개발 |
| 품질 확인 | 요청·문서·결과 비교, 검사와 남은 위험 보고 | 검토 |

팀 명세에는 **선택한 활성 역할만** 적는다. 위 표 전체를 활성 스킬 목록으로 복사하지 않는다. 기본은 `기획·콘텐츠`, `개발`, `검토` 책임을 한 에이전트가 순서대로 맡으며 하나의 workflow 스킬을 공유한다. 검토 단계에서는 원 요청과 결과를 다시 대조한다. 같은 에이전트의 재검사는 독립 검토라고 보고하지 않는다.

다음 팀 명세 틀에서 스킬 경로와 검사 대응이 한 곳에 모이도록 한다.

```text
운영: 단일 에이전트가 아래 역할을 순서대로 수행한다.
활성 역할 표의 열: role_id | 담당 책임 | skill_id
  planning-content | 제품·콘텐츠 | 실제 프로젝트 ID-workflow
  development      | 게임 구현·UI·플랫폼·공용 데이터 | 같은 workflow 스킬 ID
  review           | 품질 확인 | 같은 workflow 스킬 ID
스킬 경로: .agents/skills/<skill_id>/SKILL.md
담당 선택: 범위·결정은 planning-content, 작성은 development, 검사는 review
전달: 공용 형식 변경 시 01_contract.md, 실제 역할 전달 시 02_<role_id>.md
실패: 구현 오류는 수정 후 관련 검사 재실행, 요구 충돌은 제안 결정과 질문
완료: 검사·미실행·미정·다음 작업을 04_closeout.md에 기록
```

반복되는 전문 작업이 실제로 생길 때 Godot 자산 관리·애니메이션·오디오·네트워크 등의 스킬을 추가한다. 엔진 선택만으로 모든 전문 스킬을 만들지 않는다. 네트워크 역할은 온라인 범위와 데이터 규칙을 정한 뒤 추가하며 특정 게임의 단계 번호를 요구하지 않는다.

여러 에이전트 실행은 사용자가 요청했거나 해당 프로젝트 지시가 허용하고, 서로 독립적인 작업과 실익이 분명할 때 별도로 선택한다. 실행 전에 담당 파일·공유 환경·통합 담당·일부 실패 시 처리를 정한다. 같은 파일 수정과 같은 기기 테스트는 순서대로 진행하거나 작업 환경을 분리한다. 자동 원격 병합 정책은 기본값에 포함하지 않는다.

### 프로젝트 전용 SKILL.md 템플릿

작은 프로젝트의 기본 workflow 스킬로 사용한다. YAML은 파일 첫 줄부터 시작하며 이름·설명은 실제 값으로 치환한다.

```markdown
---
name: {{PROJECT_ID}}-workflow
description: {{GAME_NAME}}의 요청 정리, 문서·구현 작업과 검사 기록을 순서대로 진행한다.
---

# {{GAME_NAME}} 작업 흐름

## 사용 시점
프로젝트의 문서·구현·검사 요청을 수행할 때 사용한다.
담당 책임은 docs/operations/harness/team-spec.md에서 선택한다.

## 필수 입력
사용자 목표, 포함·제외 범위, docs/INDEX.md에서 찾은 기준,
현재 운영 상태와 완료 조건. 중요한 값이 없으면 기존 파일 조사 뒤 묶어 질문한다.

## 작업 흐름
1. 기존 파일·결정·사용자 변경을 확인한다.
2. _workspace/<topic>/00_request.md에 범위와 검사를 적는다.
3. 함께 쓰는 데이터 변경이면 01_contract.md에 형식·영향·버전을 먼저 적는다.
4. 허용된 범위만 작성한다. 초기 사전 구성에서는 게임 코드를 만들지 않는다.
5. 관련 검사와 ./scripts/verify.sh를 실행한다.
6. 원 요청과 결과를 대조하고 04_closeout.md를 작성한다.

## 산출물과 검증
요청한 변경 파일, 요청·마무리 기록을 남긴다.
문서 변경은 verify-docs.sh, 역할·스킬 변경은 verify-harness.sh로 확인한다.
실패·미실행 이유와 재개 조건을 남긴다. 실행하지 않은 검사는 통과가 아니다.
```

전문 스킬을 분리한다면 사용 시점을 구체적인 요청으로 좁히고 필수 입력·출력·검사도 그 책임에 맞춰 바꾼다. 범용 workflow를 이름만 바꿔 여러 개 만들지 않는다. 팀 명세에서 사용하지 않는 스킬은 활성 스킬로 남기지 않는다. 기존에 다른 용도의 스킬이 있으면 삭제하지 말고 별도 용도와 검사 범위를 기록한다.

## 4. 기본 작업 절차와 기록

`docs/operations/ai-development.md`에는 다음 절차를 넣고, 다른 문서에서는 이 파일을 연결한다.

1. README·색인·현재 상태·승인 결정을 확인한다.
2. `_workspace/<topic>/00_request.md`에 목표·범위·제외·완료 조건·검사를 적는다.
3. 필요한 경우만 설계·전달·별도 품질 확인 기록을 추가한다.
4. 정한 범위의 문서나 코드를 작성한다. 새 기능 개발부터 자동 테스트 또는 이름 있는 수동 재검사를 정한다.
5. 관련 검사 후 원 요청과 결과를 비교한다. 실패는 원인을 고쳐 다시 확인한다.
6. `_workspace/<topic>/04_closeout.md`에 실제 변경·검사·남은 일을 적는다.

기본 기록 두 개 외에는 다음 조건일 때만 추가한다.

| 조건 | 파일과 내용 |
| --- | --- |
| 공용 데이터·ID·저장·통신 형식 변경 | `01_contract.md`: 이전·새 형식, 사용하는 곳, 버전·이전 데이터 처리, 검사 |
| 실질적인 역할 전달 | `02_<role_id>.md`: 전달 입력·출력, 담당 경로, 미해결 사항, 다음 담당 |
| 별도 품질 확인이 필요한 변경 | `03_qa_rNN.md`: 확인자, 요청 대비 결과, 검사 증거, 수정 요청·재검 결과 |

작업 이름은 소문자 영문·숫자·하이픈으로 쓴다. 같은 구성 작업을 재개하면 기존 `_workspace/bootstrap/` 기록에 날짜별로 덧붙인다. 별도 요청이면 새 topic을 정한다. 기존 종료 기록을 지우거나 매번 번호만 바꾼 복사본을 만들지 않는다.

```text
00_request.md 필수 필드
  날짜 / 사용자 목표 / 기존 상태 / 포함·제외 범위
  반드시 지킬 조건 / 변경 예정 파일 / 완료 조건 / 검사 계획

04_closeout.md 필수 필드
  상태: 완료 또는 미완료와 이유
  생성·수정 파일 / 실제 검사 명령·결과·증거 위치
  실패·미실행·재개 조건 / 미정 결정 / 다음 개발 작업
  Git 작업을 요청받아 했다면 브랜치·commit·PR·되돌리는 방법
```

## 5. 순서가 정해진 초기 구성 절차

| 순서 | 할 일 | 단계 산출물 |
| --- | --- | --- |
| 1. 기존 파일 확인 | 현재 폴더·상위 지시·README·색인·스킬·검사·Git 변경 상태 확인. Git이 없어도 진행 | 요청 기록의 기존 상태·보존 목록 |
| 2. 입력 정리 | 기존 근거를 입력 양식에 반영, 중요한 누락·충돌을 묶어 질문. 나머지는 제안 | 이름·ID와 범위, 미정 결정 |
| 3. 공통 문서 | 2절의 문서와 4절의 기록 생성·보완. 모든 새 문서를 색인에 연결 | README·AGENTS·색인·제품·기술·콘텐츠·작업 절차 |
| 4. 역할·스킬 | 일곱 책임을 최소 역할에 배정, 팀 명세·운영 색인·필요 스킬 작성 | 일치하는 역할·스킬, 현재 명령·미확인 목록 |
| 5. 선택 구성 | 아래 6절에서 선택한 항목만 추가. 미선택·미정은 이유와 함께 기록 | 선택 구성 문서·준비 상태 |
| 6. 검사 | 마무리 기록을 `검사 진행 중`으로 먼저 만들고 7절의 검사 도구 작성·실행, 정상·실패 시나리오 확인 | 검사 결과·수정 내용·미실행 이유 |
| 7. 완료 기록 | 완료 조건 대조, 요청 기록에서 실제 마무리까지 연결 | 04_closeout.md와 사용자 보고 |

기존 프로젝트에서는 1단계 결과로 `유지 / 보완 / 새로 생성 / 충돌로 확인 필요` 목록을 먼저 만든다. 기존 문서 경로·엔진 버전·스킬·검사 명령을 존중한다. 요청과 관련 없는 사용자 변경을 되돌리거나 커밋에 섞지 않는다.

재실행 시 파일 존재만으로 건너뛰지 말고 필수 내용도 확인한다. 같은 역할·문서·결정을 중복 생성하지 않는다. 이미 승인된 결정을 제안으로 되돌리지 않는다. 부분 실행으로 파일이 빠졌으면 누락 파일만 보완하고 검사를 다시 실행한다. 기존 결정과 새 요청이 충돌하면 충돌 내용을 남기고 해당 부분만 답변을 기다린다.

## 6. 선택 구성

### Godot를 선택했을 때

`docs/engineering/godot/setup.md`와 `resource-rules.md`를 추가하고 색인에 연결한다. 게임 프로젝트 파일과 Autoload(엔진 시작 때 자동으로 준비되는 객체) 코드는 구현 단계에서 만든다.

- setup: 선택한 Godot 버전·선택 근거, 설치 여부, 향후 편집기·화면 없는 검사·내보내기에 필요한 환경을 기록한다. 아직 만들지 않은 프로젝트의 실행 명령은 `구현 후 사용할 예정`으로 표시한다.
- resource-rules: 코드가 실제 파일 경로 대신 논리 자산 ID를 사용하도록 설계한다. 예: `ui.confirm` → 파일 경로. ID 규칙·등록 담당·누락 처리·품질별 대체 규칙을 정한다.
- 등록 목록의 예정 경로는 `assets/resource-registry.json` 등 새 프로젝트에 맞게 정한다. 필드는 논리 ID, 종류, 실제 경로, 품질별 경로, 제작·승인 상태, 출처 기록 위치를 포함한다. 현재 자산이 없으면 목록은 빈 상태로 두며 가짜 파일 경로를 등록하지 않는다.
- 향후 검사는 ID 중복·실제 파일 누락·잘못된 품질 참조·등록하지 않은 ID 사용을 확인하도록 계획한다. 등록 목록이 비어 있음을 오류로 보지 않는다.
- 다른 프로젝트의 자산 관리자 이름·카탈로그 경로·승인 캐릭터를 복사하지 않는다. 승인과 등록은 별개이며 등록만으로 게임 연결 완료라 기록하지 않는다.

### Android를 선택했을 때

`docs/engineering/android.md`를 만들고 다음 검증 계획을 기록한다. 초기 구성에서는 SDK 설치·기기 페어링·패키지 생성·스토어 연결을 실행하지 않는다.

| 확인 영역 | 계획할 내용 |
| --- | --- |
| 화면·터치 | 방향, 가로세로 비율 표본, 화면 가장자리·안전 영역, 터치 크기·동시 입력·입력 취소 |
| 중단·복귀 | 홈 이동·잠금·전화 등 중단 후 입력 초기화·소리·상태 복원 |
| 성능 | 목표 FPS·프레임 시간·메모리·발열·배터리의 제안값, 측정 기기·상황·방법 |
| 패키징 | 패키지 ID 결정 상태, 개발·출시 빌드 구분, 서명 정보의 별도 보관 계획 |
| 결과 기록 | 자동 검사 / 에뮬레이터 / 물리 기기를 별도 행으로 기록, 날짜·환경·버전·증거·미확인 포함 |

기기가 없으면 물리 기기 검사는 미실행이다. 에뮬레이터에서 실행됐다는 사실로 물리 기기 통과를 대신하지 않는다. 터치 게임의 데스크톱 키보드 테스트도 터치 확인을 대신하지 않는다.

### 이미지·모션·오디오 준비

콘텐츠 문서에 `제작 → 검토·승인 → 등록 → 실제 게임 연결 → 연결 검사`를 각각 다른 상태로 기록한다. 프로젝트가 요구하는 승인 담당과 방법을 먼저 정한다. 사용자 승인 요구를 정했다면 제작 요청만으로 승인 상태를 바꾸지 않는다.

자산별 기록 필드: 자산 ID, 종류, 원본·파생 파일 경로, 제작자·생성 방법, 원본 URL 또는 제공 경로, 확인 날짜·버전, 이용 조건과 근거, 수정 내용, 승인자·날짜·대상 버전, 등록 위치, 실제 사용 위치, 연결 검사 결과. 해당하지 않으면 이유를 쓰며 `권리 미확인`을 허가로 취급하지 않는다. 이미지가 없어도 임시 도형으로 개발을 진행할 계획을 둔다. 초기 구성에서 최종 이미지나 모션을 생성할 필요는 없다.

### 플러그인·디자인 도구·Git 원격

선택 도구는 `필요성 / 선택 기준 / 현재 준비 상태 / 필요한 별도 요청 / 대체 방법`을 운영 색인에 기록한다. 도구가 없으면 로컬 문서와 임시 자산으로 진행한다. 연결되지 않은 서비스의 파일을 읽었다고 기록하지 않는다.

| 선택 항목 | 선택 기준·준비 상태 확인 | 설정 예시와 별도 요청 |
| --- | --- | --- |
| 플러그인 | 필요한 기능, 지원 환경, 사용 권한, 설치·연결 여부를 가능한 읽기 전용 방법으로 확인 | `도구: 후보 / 기능: 이미지 제작 / 상태: 미설치 / 대체: 임시 도형`. 설치·계정 연결은 별도 요청 |
| 디자인 도구 | 화면 설계 필요, 편집·내보내기 지원, 원본 소유·접근 권한 | `원본 문서: 미정 / 편집자: 미정 / 내보내기 위치: assets/ui/`. 원격 파일 생성·권한 변경은 별도 요청 |
| Git 원격 | 협업·백업 필요, 기존 저장소·브랜치·변경·원격 유무 확인 | `원격: 미설정 / 통합: 로컬 변경 검토 후 결정`. 원격 추가·push·PR·병합 정책 설정은 별도 요청 |

위 예시는 값의 형식이다. 비밀번호·토큰·서명 키를 문서에 적지 않는다. 도구가 이미 준비돼 있어도 이번 사전 구성에 필요하지 않으면 호출하지 않는다. 사용자가 별도로 설치·연결·원격 작업을 요청하면 그 범위의 절차를 적용한다.

## 7. 생성할 검사 규칙과 완료 판단

Codex는 `tools/verify_bootstrap.py`를 Python 3 표준 라이브러리로 작성한다. 구조 검사에는 엔진·플러그인·네트워크·외부 패키지가 필요하지 않게 한다. Python 3가 없다면 도구 설치를 임의 실행하지 말고 검사 파일을 작성한 뒤 미실행 이유와 필요한 환경을 보고한다.

검사 도구는 실행 위치와 무관하게 자신의 파일 위치에서 프로젝트 루트를 찾고, `--scope docs|harness|all`을 받도록 만든다. 성공은 종료 코드 0, 실패는 0이 아닌 코드와 `파일: 문제: 수정할 내용`을 출력한다. 검사 때문에 파일을 수정하지 않는다.

| 범위 | 필수 검사 규칙 |
| --- | --- |
| docs | 2절의 필수 문서·요청·마무리 기록 존재, 내용이 빈 파일이 아님, 선택 구성 문서 존재, 색인에서 모든 기준 문서에 접근 가능 |
| docs | README·AGENTS·docs의 Markdown 상대 링크 대상 존재. 코드 블록·인라인 코드의 예시와 외부 URL은 제외. `#` 뒤 제목 링크는 해당 문서의 제목과 맞는지 확인 |
| harness | 팀 명세 활성 역할 표의 role_id 중복 없음, 각 역할의 담당 책임과 skill_id 존재, 일곱 책임이 빠짐없이 배정됨 |
| harness | 활성 skill_id의 집합과 실제 프로젝트 전용 스킬 폴더 집합 일치. 여러 역할이 한 스킬을 쓰는 것은 허용 |
| harness | SKILL.md 첫 부분의 YAML 구분자·name·description, 폴더와 name 일치, 네 필수 제목과 내용 확인 |
| all | 위 두 범위와 검사 파일 존재, 운영 색인의 실제 명령과 스크립트 경로 일치, 미치환 `{{...}}`와 복사 금지 식별자 탐지 |

링크 검사에서는 URL 디코딩·상대 경로·제목의 공백과 구두점 처리를 정하고, 지원하지 않는 링크 형식은 자동 통과시키지 말고 이름 있는 수동 확인 항목으로 보고한다. 스킬 YAML은 이 지침의 단순한 문자열 필드 형태로 만들면 표준 라이브러리만으로 확인할 수 있다. 기존 복잡한 YAML은 임의로 깨뜨리지 말고 지원 여부와 필요한 수동 확인을 보고한다.

필수 파일 경로·선택 구성·활성 스킬 검사 범위는 검사 도구 상단의 명시적인 설정으로 관리한다. 기존 프로젝트 경로를 존중해 바꾸되 필수 책임을 누락하지 않는다. 역할 목록은 팀 명세에서 읽고 검사 코드에 별도 복사하지 않는다. 원래 있던 다른 용도의 스킬은 좁은 경로 목록과 이유로 구분한다.

이 지침서 자체를 새 프로젝트에 보관한다면 예시 토큰·이름 탐지에서 **그 파일 하나만** 제외한다. 생성된 문서 전체, `_workspace/` 전체 또는 스킬 전체를 제외하지 않는다. 승인되지 않은 게임 코드의 존재를 검사로 강제하거나 기존 게임 코드를 삭제하지 않는다.

식별자 검사는 생성한 안내·설정·명령·스킬·작업 기록을 대상으로 한다. 검사 도구 자신의 탐지용 문자열 상수는 실제 프로젝트 설정과 구분해 그 정의 부분만 제외한다. 검사 규칙에 들어 있는 금지어를 프로젝트 이름이 잘못 복사된 것으로 판정하지 않도록 정상 표본에서 확인한다.

세 셸 명령은 다음 내용으로 만들고 실행 권한을 준다. 기존 명령이 있으면 보존하고 구조 검사를 연결한다. 셸이 없는 환경에서는 대응하는 Python 명령을 README·운영 색인에 함께 기록한다.

```sh
#!/bin/sh
# scripts/verify-docs.sh
set -eu
ROOT=$(CDPATH= cd -- "$(dirname -- "$0")/.." && pwd)
exec python3 "$ROOT/tools/verify_bootstrap.py" --scope docs
```

```sh
#!/bin/sh
# scripts/verify-harness.sh
set -eu
ROOT=$(CDPATH= cd -- "$(dirname -- "$0")/.." && pwd)
exec python3 "$ROOT/tools/verify_bootstrap.py" --scope harness
```

```sh
#!/bin/sh
# scripts/verify.sh
set -eu
ROOT=$(CDPATH= cd -- "$(dirname -- "$0")/.." && pwd)
exec python3 "$ROOT/tools/verify_bootstrap.py" --scope all
```

게임 실행 검사는 게임 구현 이후 실제 환경이 갖춰졌을 때 추가한다. 구조 검사 통과를 게임 실행·플랫폼 지원 완료라고 보고하지 않는다.

### 이름 있는 재검사: bootstrap-six-scenarios

검사 도구를 만든 뒤 임시 폴더의 최소 표본에서 정상과 실패 흐름을 확인한다. 실제 사용자 파일을 지우거나 잘못된 값으로 바꾸며 시험하지 않는다.

| 상황 | 기대 동작과 확인할 결과 |
| --- | --- |
| 빈 프로젝트 | 필수 입력 확인 후 공통 파일·최소 스킬·검사 생성. 게임 코드 없이 구조 검사 통과 |
| 기존 프로젝트 | 같은 역할의 기존 문서·명령 유지, 빈 곳만 보완. 기존 결정·사용자 변경 보존 |
| 엔진 미정 | 제안 결정과 공통 구성 완료. Godot 파일·엔진 설치·실행 검사를 강제하지 않음 |
| 선택 도구 없음 | 플러그인·디자인 도구·Git 원격 없이 구성과 구조 검사 가능 |
| 구성 재실행 | 두 번째 실행의 변경 비교에서 중복 문서·스킬·결정 없음. 날짜별 기록 외 불필요한 변경 없음 |
| 필수 파일 누락 | 임시 표본의 필수 파일 하나 제거 시 검사 실패·경로 출력. 복원 후 통과. 잘못된 스킬 이름·끊어진 링크·미치환 ID도 각각 실패 확인 |

새 프로젝트 구성 실행자는 각 상황을 실제 표본 실행 또는 문서 검토 중 어떤 방법으로 확인했는지 구분해 기록한다. 문서만 검토했다면 검사 도구의 실제 실패 탐지까지 검증됐다고 보고하지 않는다.

### 완료 조건과 보고 형식

- 중요 입력이 확정됐거나 사용자가 미정 유지를 선택했고, 남은 항목이 제안 결정에 연결돼 있다.
- 필요한 파일이 실제로 작성됐고 색인·팀 명세·스킬·명령이 일치한다.
- 구조 검사를 실행해 통과했다. 실행 불가·실패가 있으면 전체 완료 대신 미완료와 이유를 기록한다.
- 기존 파일·결정 보존과 재실행 절차를 확인했고, 게임 코드를 사전 구성에 추가하지 않았다.
- 요청·마무리 기록에 변경·검사·미정·다음 작업이 있다.

최종 보고는 다음 항목을 짧게 작성한다.

```text
결과: 사전 구성 완료 또는 미완료와 이유
생성·수정: 실제 파일 경로와 변경 목적
검사: 실제 명령 / 통과·실패·미실행 / 환경·증거
시나리오: 상황별 표본 실행 또는 문서 검토 결과
남은 확인: 실패·미실행 이유와 재개 조건
미정 결정: 결정 ID와 사용자에게 필요한 선택
다음 개발: 첫 플레이 흐름의 구체적인 구현·검사 작업
```

## 8. Forest Arena 경험과 참고 자료

아래 연결은 이 문서의 설계 근거다. 다른 프로젝트의 Codex가 열거나 복사할 필요는 없다. 과거 기록의 단계·역할 수는 당시 상태이며 새 프로젝트의 기본값이 아니다.

| 경험 | 새 프로젝트 준비 규칙 | 참고 근거 |
| --- | --- | --- |
| 문서 이동 후 오래된 경로가 남을 수 있음 | 색인을 시작점으로 만들고 상대 링크·누락 파일 검사 | [문서 색인과 이동 경로](../INDEX.md), [하네스 정리 기록](../../_workspace/project-harness-cleanup/04_closeout.md) |
| 역할 통합 뒤 여러 곳의 목록이 어긋날 수 있음 | 팀 명세 한 곳만 활성 목록으로 사용, 스킬과 자동 비교 | [팀 명세](harness/team-spec.md), [하네스 통합 기록](../../_workspace/harness-consolidation/04_closeout.md) |
| 모든 작업에 많은 기록을 요구하면 불필요한 파일이 늘어남 | 요청·마무리는 항상, 공용 형식·전달·별도 검토는 필요한 경우만 | [작업 절차](ai-development.md), [팀 명세의 작업 증적](harness/team-spec.md#작업-증적) |
| 승인 자산을 등록해도 실제 화면 연결은 별도 작업임 | 제작·승인·등록·연결·검사 상태 분리, 출처·이용 조건 기록 | [콘텐츠 원칙](../content/art-and-audio.md), [전투 UI 연결 기록](../../_workspace/combat-resource-ui/04_closeout.md) |

Forest Arena의 단계 번호, 캐릭터·전투·성장 규칙, 패키지 ID, DB·LAN 구성과 자동 원격 병합 정책은 이 프로젝트의 선택 결과다. 새 게임의 공통 기본값으로 복사하지 않는다. 이 문서의 공통 규칙은 문서 탐색·책임 구분·작업 기록·구조 검사이며, 게임과 서비스의 선택은 새 입력과 승인 근거로 정한다.
