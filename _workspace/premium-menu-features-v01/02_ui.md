# 실제 메뉴 기능과 앱 연결

2026-10-15. ADR-033과 [공용 계약](01_contract.md)에 따라 v07 네이티브 메뉴의 미션·친구·랭크·프로필을 실제 기기 기록과 개발 서버에 연결했다. 기존 캐릭터·장신구·편성·상점·일반 설정·조작 화면의 구성과 논리 자산 ID를 유지한다.

## 화면과 사용자 동작

- 미션은 일일·주간·누적 분류, 실제 진행 수치, 완료 표시와 상세 확인을 제공한다. 한국 시간 자정·월요일 경계를 사용한다. 연습·Story·포기는 제외하며 보상은 없다.
- 친구는 정확한 닉네임 검색, 요청·수락·거절·취소·삭제, 접속 여부, 최근 LAN 상대와 초대를 제공한다. 실제 LAN 호스트 대기방이 있을 때만 친구 초대가 가능하다. 이미 경기나 LAN 방에 들어가 있으면 다른 초대 수락 전에 현재 방을 닫도록 안내한다.
- 랭크는 전체·한국 시간 이번 달·친구 범위와 페이지 이동, 내 순위를 제공한다. 서버가 집계한 정상 LAN 결과를 표시하며, 오프라인 기록은 순위에 넣지 않는다. 0경기는 순위 없음으로 표시한다.
- 프로필은 현재 편성과 보유 정보, 닉네임 편집, 계정 연결, 오프라인 전체와 AI·Solo·Team별 기록, 별도 LAN 전적과 최근 완료 기록을 제공한다.
- 로컬 기록, 계정 미연결, 조회 중, 연결 오류, 성공한 빈 목록을 구분한다. 이전 조회 자료를 보여 줄 때 조회 시각을 표시한다. 현재 기간을 확인할 수 없는 오래된 미션 자료에는 다시 연결할 안내를 표시한다.
- 친구 화면을 보는 동안 10초마다 다시 조회하고, 접속 상태는 30초마다 갱신한다. 다른 화면으로 나가면 친구 조회를 멈춘다. 검색·닉네임·주소 입력은 초안에 남기고 조회 후에도 입력 포커스와 커서 위치를 복원한다.
- 주요 버튼·입력의 실제 72px 크기와 안전 영역, 1.0·1.15·1.3 글자 크기, 배경 확장, 스크롤과 전체 메뉴를 유지한다. 화면 PNG를 메뉴 대신 붙이지 않는다.

## 앱 서비스 API

`MenuServiceClient`는 Node이며 앱의 `menu_service`로 연결한다. `configure(app)`는 로컬 기록만 읽고 네트워크를 강제하지 않는다. `record_offline(config, controller)`, `refresh_menu(menu_id)`, `foreground(value)`, `snapshot(menu_id)`, `perform(action, payload)`, `lan_session(api_url)`를 제공한다. 서비스 변경은 `changed(menu_id)` 신호로 라우터에 알린다.

`snapshot()`은 status(local/unlinked/idle/loading/ready/error), data, error, binding, intent와 전송 대기 수를 제공한다. 화면은 이 값을 읽으며 승패를 다시 계산하지 않는다. 단위 검사에는 `request_adapter(url, method, route, payload, token)`으로 전송 응답만 바꿀 수 있다. 이 도구는 실제 배포 기본값에 가짜 목록을 넣지 않는다.

루트 앱의 `apply_unified_identity(response) -> bool`은 프로필과 DB·LAN 세션을 저장한 뒤 실행 중 값을 바꾼다. `join_menu_invite(code)`는 실제 LAN 참가 흐름을 연다. `return_menu_lan_room()`은 친구 메뉴에서 호스트 대기방으로 돌아간다. LAN 경기 결과는 앱의 오프라인 전송을 거치지 않고 경기 서버의 별도 결과 저장을 사용한다.

## 계정과 저장 복구

새 파일은 기존 프로필 v3 및 메뉴 프리셋·조작 v1과 분리한다.

| 파일 | 내용 |
| --- | --- |
| `menu_identity_v01.json` | 연결된 서버·원본/통합 사용자 ID, 통합 요청, 성공 응답, 미확인 친구 요청 |
| `menu_progress_v01.json` | 완료 이벤트 ID와 출처 사용자·서비스, 전송 대기 여부, 서버 조회 자료 |

두 파일은 버전 1이며 임시 파일·백업을 사용한다. 읽을 수 없는 원본·백업 또는 알 수 없는 버전은 쓰기를 막아 초기값으로 덮지 않는다. 저장 실패 때 실행 중의 이전 기록을 유지한다.

계정 연결은 저장된 DB 계정, LAN 게스트, 새 게스트 순서다. 같은 서비스 ID를 확인한 뒤 원본 토큰의 소유 증명과 최종 닉네임, 현재 프로필을 보낸다. 다른 서비스 ID는 자동 통합하지 않는다. 보유 합집합은 서버가 처리하며 기기 프리셋 4개는 통합 사용자 이름으로 복사한다. 기존 프리셋과 조작 파일을 지우지 않는다.

통합 request_id와 원문, 현재 편성은 네트워크 요청 전 원본·백업 양쪽에 저장한다. 응답 손실과 재시작 뒤 같은 원문으로 재전송한다. 서버 성공 응답은 앱 파일 변경 전에 저장하며, 일부 파일만 저장된 경우에도 같은 작업으로 이어간다. 성공 응답에 예전 토큰이 있더라도 현재 원본 사용자와 일치하는 최신 저장 인증을 다시 확인한 뒤 적용하여 갱신된 토큰을 되돌리지 않는다. 미커밋 원본 증명의 재인증 오류는 원래 계정을 유지하고 새 증명으로 다시 연결하도록 안내한다.

계정·서버·모드·요청 세대가 바뀌어 뒤늦게 도착한 응답은 새 계정에 적용하지 않는다. 통합 요청이 남아 있으면 기존 프로필 변경을 먼저 확인하도록 앱과 연결한다. LAN 방이 열려 있으면 통합·닉네임 변경을 막아 실제 참가자의 신원을 유지한다.

## 기록과 중복 방지

오프라인 결과는 유효한 AI·Solo·Team 경기 설정과 실제 완료 상태를 확인한 뒤 기록한다. 컨트롤러에 같은 이벤트 ID를 유지하여 결과 화면의 중복 호출을 막는다. 저장하지 못한 이벤트는 성공으로 표시하지 않고 오류와 실행 중 재시도 대상으로 남긴다.

전송 대기 이벤트는 원본 사용자와 서비스·통합 사용자 ID로 분리한다. 다른 계정이나 다른 서비스에는 보내지 않는다. 서버 전송 확인 뒤 조회가 실패하면 대기 기록을 유지한다. `/progress` 조회 성공과 이벤트 전송 완료 표시는 하나의 파일 저장으로 함께 반영한다. 미션과 프로필은 같은 조회 자료를 공유하므로 한쪽에서 확인한 뒤 다른 화면에서 기록이 사라지거나 중복 합산되지 않는다. 캐릭터 누적 미션은 전체 서버 캐릭터 집합과 미전송 캐릭터를 합집합으로 확인한다.

친구 동작은 대상 요청 ID와 별도로 operation_id를 요청 전 저장한다. 결과를 잃으면 같은 ID와 내용으로 재확인한다. 초대 수락은 현재 경기·방을 바꾸기 전에 사용 가능한 상태인지 확인한다. 비밀 토큰과 인증 원문을 검사 결과나 로그에 출력하지 않는다.

## 검사와 증거

- `tests/menu_feature_store_unit.gd`: 저장·백업·중복·한국 시간 경계·사용자별 대기 전송·알 수 없는 버전 차단과 50개 초과 전송 대기 표시 31개 검사 통과.
- `tests/menu_service_client_unit.gd`: 응답 손실, 동일 통합 재전송, 캐시와 이벤트의 동시 저장, 저장 실패 뒤 중복 없는 표시, 성공 응답과 인증 회전 복구, 친구 요청 재전송, 계정 변경 뒤 늦은 응답, 다른 서비스 차단, LAN 중 통합·초대 차단, 10초 조회와 화면 이탈 중단 등 63개 검사 통과.
- 두 단위 검사를 `scripts/verify.sh`에 추가했다. 실제 앱 시작으로 클래스와 연결 함수 파싱을 확인했다.
- 기존 네이티브 검사 `tests/premium_menu_runtime.gd`는 이번 작업 폴더로 결과 경로를 옮기고, 기존 역사 증거를 덮지 않는다. 81개 상태의 미션 상세와 친구·접속·오류·빈 검색은 고유한 버튼·응답 상태까지 검사한다. 전송 표본은 검사 자료임을 명시하고 실제 PostgreSQL 확인과 구분한다.
- 실제 서버 연결과 독립 품질 확인은 QA 기록을 따르며, 실제 화면 PNG·APK는 통합 역할이 생성한다. 이 역할에서 Android 실기기 통과를 기록하지 않았다.

최종 기본 네이티브 재검사는 3,091개 항목을 통과했다. 미션 상세 3개와 친구 행·연결 오류·빈 검색의 고유한 화면 상태를 각각 실행했으며, 검사 응답 표본과 실제 서버 확인의 범위를 결과 JSON에 구분했다.

최종 인증 복구 검사에는 LAN 게스트만 있는 통합 의도도 포함했다. 최신 인증 후보는 같은 원본 ID의 DB 파일, LAN 파일, 통합 의도 순서로 찾는다. 현재 실행 중 인증을 재사용하려면 refresh token까지 일치해야 하고 진행 중인 인증 갱신이 없어야 한다. LAN 파일에 이미 저장한 다음 토큰이 있으면 그 값을 그대로 이어받아 서로 다른 후속 토큰을 만들지 않는다. 성공 응답은 재전송하지 않고 최신 인증으로 기기 저장만 마무리하는 경우를 확인했다.
