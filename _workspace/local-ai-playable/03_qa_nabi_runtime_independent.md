검토 중 발견한 승인 날짜 오류는 통합 담당 수정 뒤 재확인하여 해결했다. 신규 manifest는 1단 모션 승인2026-09-26과 로컬 처리 승인2026-10-01을 분리하고, 2단 모션·처리 승인 및 두 항목의 검증 날짜를2026-10-01로 기록한다. 기술적 통과를 승인 일자 소급으로 해석하지 않는다.

## 독립 확인 증거

- 승인 검토 PNG 두 파일을 `git show HEAD:<path>`의 바이트와 직접 비교해 동일함을 확인했다. 정규화 스크립트는 입력을 열어 읽고 `normalized` 출력 폴더만 기록한다. 승인 원본은 비변경이다.
- 두 런타임 PNG를 Pillow로 직접 읽어 각각 2048×128, RGBA, alpha 최솟값0/최댓값255, 16개 128×128 셀을 확인했다. 각 셀의 비어 있지 않은 영역이 셀 안에 있고 하단 경계는 모두 y=124다(실제 마지막 불투명 픽셀 행은123).
- 1단 가시 영역 전체 범위 x=9–114, 2단 x=10–124다. 2단 발톱을 포함해 셀 경계에 닿지 않으며 오른쪽4픽셀 이상 여백을 보존한다.
- 실제 파일 SHA-256은 manifest와 일치한다. 1단 `4e3952c533c912fa7f37bd9ab8ea186662ed52b13eecafd58952fc8057d84804`, 2단 `2679b0eb310359762f4099b9bed167c6ae5020b1c0860679be60e30b69366fe1`.
- 두 정규화 contact PNG를 직접 보았다. 흰 귀 두 개·꼬리 한 개·인간형 손발·검정/보라 의복·발톱을 유지하고 명백한 잘림이나 새 동물형 신체가 없다. 2단 순서는 승인 검토 순서를 적용한다. 미세한 원본 포즈 크기 차이는 남아 있으며 재그림하지 않았다.
- SpriteFrames는 각 시트의 x=0부터1920까지128 간격인16개 AtlasTexture를 참조한다. 12FPS, 비루프, 정확한 `attack_light_combo_01/02` 이름을 사용한다. manifest에 같은 나비 motion ID 중복은 없다.
- `phase_frame_ranges`는1단 `[0,4), [4,8), [8,16)`, 2단 `[0,5), [5,8), [8,16)`이며 준비·활성·회복 상태의 공격 tick을 읽어 해당 범위 안에서만 frame을 고른다. 실제 공격 준비/활성/회복 tick과 적중 판정은 기존 AttackData/전투 계산이 소유한다. 이 FPS는 적중 시계가 아니다.
- 표시 배율1.2와 foot pivot124를 사용하더라도 화면 발 기준선은 fighter의 y+14에 맞도록 위치를 보정한다. 기본 모션은 기존 배율1·기준선128 기본값을 유지한다.

## 남은 한계

위 검사는 파일·데이터·표현 로직과 접촉 시트 품질이다. 실제 Android 작은 화면에서 연계·좌우 반전 재생·모든 배경의 가장자리 잔상 및 성능을 확인한 것으로 바꾸지 않는다. 두 RGBA 텍스처의 원시 메모리 합계는 mipmap 등을 제외하고 약2MiB이나 실제 GPU 사용량은 기기에서 측정해야 한다. 실기기는 연결이 끊긴 상태로 전달됐으며 이 독립 QA에서도 확인하지 않았다. 전체 신규 모션과 로컬 AI 목표 완료 승인은 여전히 보류한다.
