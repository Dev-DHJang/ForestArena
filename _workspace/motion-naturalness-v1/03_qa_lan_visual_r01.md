# 실제 LAN 피격 후반 연결 — 독립 시각 QA r01

판정: **PASS — 네 경우의 공개 presentation 실소켓 fixture 범위**. 자현·나비 × 정상·반전에서 원격 클라이언트와 해당 파이터를 소유한 클라이언트의 피격 후반 연결을 확인했다. 실제 앱 HUD 영상이나 Android 기기 검사로 확대하지 않는다. 이 통과는 후보 모션의 사용자 승인을 대신하지 않는다.

## 입력과 독립 재검산

검토 원본은 `qa/lan-launch-release-capture-r02/`, 실행 fixture는 `qa/lan-launch-release-visual-r03/`다. 기존 실패 `capture-r01`과 이전 fixture r02는 보존했다. 이번 QA는 새 소켓 실행을 반복하지 않고 root가 실행한 네 실제 연결 결과와 원본 픽셀을 독립 검토했다.

| 대상 | 원 실행 검사 수 | 양 클라이언트 PNG | 실제 release 그림 번호 | 판정 |
| --- | ---: | ---: | --- | --- |
| 자현 정상 | 2,561 | 74 | 각각 13→14→15→16 | pass |
| 자현 반전 | 2,567 | 74 | 각각 13→14→15→16 | pass |
| 나비 정상 | 2,509 | 80 | 각각 13→14→15→15→16 | pass |
| 나비 반전 | 2,499 | 78 | 각각 13→14→14→15→16 | pass |

합계는 원 실행 **10,136검사**, 원본 PNG **306장**이다. 검사 수는 원 보고서의 합계를 다시 계산한 값이며 독립 QA 스크립트의 assertion 개수로 바꿔 부르지 않았다. 같은 그림의 연속 표시는 실제 delta에 따른 유지이며, 서로 다른 네 그림의 순서는 모두 확인됐다.

`qa/lan-launch-release-code-independent-r01/check-actual-capture-r02.py`를 실행해 다음을 재검산했다. 결과는 `qa/lan-launch-release-visual-independent-r01/independent-proof.json`에 있다.

- 시작 전·종료 후·현재 파일의 **2,828개 소스 SHA**가 모두 같다. r10 catalog SHA도 일치한다.
- 네 child 보고서의 SHA와 정상 종료·오류 0, auth/server/client 로그의 오류 문구 0을 대조했다. sync/draw 연결 누락과 어느 쪽에도 관찰되지 않은 snapshot은 모두 0이다.
- 압축본 8개의 GZIP SHA, 압축 해제 RGBA SHA, 남아 있는 원시 RGBA 전체 바이트, PNG 306장의 RGBA가 모두 일치한다. 원시 파일은 삭제하지 않았다.
- PNG 각각의 실제 픽셀에서 8byte marker를 다시 읽었다. sync 번호·그림 번호·client slot·방향·motion·XOR 검사값이 native draw 기록과 일치한다. sync/draw의 수신 snapshot·도착 번호·표시 자세·크기·위치가 일치하며 proxy의 남은 경직은 0이다.
- 각 case의 세 MOVE RELEASE barrier가 당시 관측 최대 tick+2 이상을 양쪽에서 수신했는지, 다음 PRESS·최종 heavy가 해당 tick 뒤에 전송됐는지 대조했다. 네 경우 모두 맞는다.

## 시간과 재생 자료

실제 LAN snapshot에는 남은 경직 시간이 없다. 이 기록에서도 표시 경직을 임의로 만들지 않았다. 일반 LAUNCH는 그림 5까지 보인 뒤 실제 FALL snapshot으로 넘어갔고, 선택 release `[12,16)`의 그림 13~16을 연결한 다음 실제 jump 그림 15로 바뀌었다. **LAN에서 LAUNCH 그림 6~12까지 전부 재생됐다는 뜻이 아니다.** 전체 16장 원화와 로컬 상태 재생의 검토는 기존 `03_qa_remaining_final_r04.md`에 별도로 남아 있다.

`clock-recalculation.json`에서 8개 client 구간의 elapsed 차이가 각 실제 `delta_for_sync`와 일치함을 확인했다. 종료 기준은 4/60초다. 자현은 첫 jump의 engine elapsed가 0.0666667초, 나비 정상은 0.0818714초, 나비 반전은 0.0812770초였다. 나비도 기준을 넘는 첫 실제 표시 sample에서 종료하며 한 sample을 더 연장하지 않았다. 그리기 완료 시계로 관찰한 시작→첫 jump 간격은 약 0.06656~0.09163초다. engine delta와 backend 완료 시계의 값을 같은 것으로 쓰지 않았다.

네 짧은 검토용 MP4는 양쪽 클라이언트의 같은 sync stamp 이미지를 나란히 배치했다. 각 간격은 client1의 실제 `post_draw_usec` 차이다. concat 입력과 출력 timebase를 1μs로 지정하고 ffprobe로 **37/37/40/39개 sample 모두**의 PTS를 원 시각과 2μs 미만 오차로 대조했다. 강제 60FPS, 중간 그림 추가, 네 자세를 보이기 위한 시간 확대는 하지 않았다. 마지막 관찰 이미지에는 종료 표시용 1μs tail만 붙였다. MP4는 보기 편한 H.264 파생물이며 정확한 픽셀 검증은 원본 PNG/RGBA/GZIP을 근거로 한다.

## 직접 본 범위와 관찰

306장 전체를 16개의 순서 비교판으로 직접 봤다. 네 경우 각각 양 client의 마지막 일반 LAUNCH F5→release F13/F14/F15/F16→첫 jump F15를 원래 PNG의 표시 크기로 자른 비교판 4개·8줄도 직접 대조했다. 원본 자체는 바꾸지 않았다.

QuickTime의 정식 로컬 파일 열기를 사용해 네 MP4를 각각 **1배속과 0.5배속으로 0부터 끝까지** 재생했다. 중간 재생 화면과 끝에서 정지된 UI를 확인했다. 끝 시각은 자현 정상 0.633036초, 자현 반전 0.630198초, 나비 정상 0.673096초, 나비 반전 0.659196초다. 연속 재생의 모든 순간을 개별 스크린샷으로 관찰했다고 주장하지 않으며, 모든 개별 PNG는 비교판 검토로 확인했다. `playback-observations.json`에 범위와 관찰을 남겼다.

- **자현:** F5→F13에서 뒤로 젖힌 몸의 방향을 이어 받고, F14~F16에서 다리를 접으며 몸을 앞으로 세운 뒤 공중 회복 자세로 넘어간다. 정상·반전과 owned/remote 양쪽에서 얼굴·귀·몸·목도리의 연결이 유지된다. 별도 idle을 끼우거나 큰 배율로 교체하는 모습은 없고, 마지막 자세에서 바로 공중 자세로 바뀌는 흐름을 읽을 수 있다.
- **나비:** F5→F13의 무릎 접기, F16→jump F15의 무릎 펴기·얼굴 방향 변화는 자현보다 분명하다. 느린 재생에서도 이 자세 변화는 보이지만 짧은 공중 회복으로 읽히며, 이번 네 장면의 표시 크기에서는 연결을 막는 크기 교체·잘림·idle 삽입은 보이지 않았다. 완전한 중간 안무를 더 그렸다고 표현하지 않는다.
- 두 client의 대상은 같은 `lan_guest`이며 client1은 원격 표시, client2는 소유 표시다. 둘의 입력 주체·slot을 혼동하지 않았고 정상/반전 모두 네 후반 그림을 직접 확인했다. 나비끼리의 경우에도 검토 대상은 우측에 피격되는 guest다.

## 한계와 마무리

이 fixture는 같은 작업트리의 실제 인증·WebSocket 서버와 두 client, 공개 presentation을 사용한다. 실제 앱 HUD를 통한 조작 영상, 장거리·손실 네트워크, 저성능 기기, Android 엄지 접근성·중단/복귀는 이번 검사 대상이 아니다. 기존 30FPS 최소 GPU probe의 F14 누락 FIX도 이 60FPS 환경의 네 경우 통과로 지우지 않는다.

제품·원본 그림·후보·manifest·등록 계획은 수정하지 않았다. QA 파생 비교판·재생 영상·독립 재검산 기록만 새 폴더에 만들었다. 이번 네 실제 연결과 표시 범위에서 남은 필수 fix/blocked는 없다. 모션 등록은 별도의 명시적 사용자 승인 이후 절차를 따른다.

문서 검사는 `./scripts/verify-docs.sh` 종료 코드 0으로 통과했다. 로그는 독립 결과 폴더의 `verify-docs.log`에 보존했다.
